## Repository層の責務定義

### 定義

データの永続化手段を隠蔽し、呼び出し側に永続化先（DB、ファイル、外部API等）を意識させない層。
Repositoryを通じてデータの登録・更新・取得・削除を行うことで、
安全な永続化（関連データの同期、制約の担保等）が保証される。

Service層はRepositoryに「何を永続化するか」を伝え、
Repositoryは「どのように永続化するか」を担う。

持ってはいけない責務:
- ビジネスロジックの実装（登録可否の判定、計算、状態遷移ロジック — Service層の責務）
- 複数Repositoryをまたぐトランザクション管理（Service層の責務）
- 永続化に関係しない外部サービスの呼び出し（メール送信、通知等）

### 判断基準

1. **永続化手段の隠蔽**
   - 永続化技術（SQL、ORM、ファイル操作等）が呼び出し側に漏れていないか
   - Service層やController層がORMモデルを直接操作していないか

2. **入出力の型**
   - 引数と戻り値がエンティティまたはDTOであるか
   - ORMモデルがRepository外に漏れていないか

3. **ビジネスロジックの不在**
   - Repository内にビジネス判定が存在しないか
   - データの加工が永続化のための変換に限定されているか

4. **安全な永続化の保証**
   - 関連データの同期や制約がRepository内で一貫して担保されているか
   - Repositoryを迂回してORMモデルを直接操作する経路が存在しないか

5. **インターフェースと実装の分離**
   - Service層がインターフェースに依存し、具象実装に直接依存していないか

### 欠陥パターン

- **ビジネスロジックの混入**: 「この条件なら登録しない」等のビジネス判定がRepository内に実装されている。Repositoryは永続化に専念すべき
- **ORMモデルの直接返却**: ORMモデルをそのまま返却し、呼び出し側がsave()、delete()等を直接実行できてしまう。永続化保証の迂回経路が生まれる
- **インターフェースの不在**: Service層がRepository実装に直接依存し、テスト時のモック差し替えが困難
- **永続化手段の漏洩**: Repository外でORMモデルのwhere()、save()等が直接呼ばれ、永続化手段がアプリケーション全体に散在している
- **汎用クエリメソッドの濫用**: `findByConditions(array $conditions)`等で呼び出し側がテーブル構造を知る必要がある。意図が明確な個別メソッドに分割すべき
- **関連データの同期漏れ**: 親テーブルのみ保存して関連テーブルの同期を呼び出し側に任せており、永続化保証が不完全
- **Repository間の暗黙的な依存**: あるRepositoryが別のRepositoryを内部で呼び出し、永続化対象の責任範囲が不明確
