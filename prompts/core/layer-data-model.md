## Model層（データモデル）の責務定義

### 定義

Model層とは、データベースのテーブルに対応し、
データの永続化・取得・リレーション定義を担うオブジェクトの層である。
LaravelにおけるORMモデル、Ruby on RailsにおけるActiveRecord、
SymfonyにおけるDoctrine Entity、TypeORMにおけるEntity等、
各フレームワークのORMモデルがこれにあたる。

Model層はアプリケーションにおける「データ構造の表現」と
「永続化に直結する操作」の責務を持つ。
デフォルト値や型制約等、データに密接な振る舞いはModelに持たせてよい。
ただし複雑なビジネスルールはエンティティやService層に分離すべきである。

### Model層の構成要素

1. **テーブルマッピング**
   - テーブル名、プライマリキー、タイムスタンプの定義
   - fillable / guarded によるマスアサインメント制御
   - キャストの定義（型変換）

2. **リレーション定義**
   - hasOne, hasMany, belongsTo, belongsToMany 等のテーブル間関係
   - ポリモーフィックリレーション
   - リレーションの命名（ドメイン用語を反映すべき）

3. **スコープ（Scope）**
   - 再利用可能なクエリ条件の定義
   - ローカルスコープ、グローバルスコープ

4. **アクセサ / ミューテタ**
   - 取得時・保存時のデータ変換
   - 表示用のフォーマット変換

5. **ライフサイクルフック**
   - creating, created, updating, updated 等のイベント
   - Observer パターンによるフック

### Model層が持つべき責務

- テーブル構造（カラム、型、デフォルト値）の表現
- テーブル間のリレーション定義
- マスアサインメント制御（fillable / guarded）
- 型キャスト定義
- 再利用可能なクエリ条件のスコープ定義
- アクセサ / ミューテタによるデータ変換
- ソフトデリート等の永続化に関わる振る舞い定義

### Model層が持ってはいけない責務

- ビジネスルールの実装（条件判定、計算、状態遷移ロジック）
- 複数テーブルにまたがるトランザクション制御
- 外部サービス（API、メール、通知等）の呼び出し
- HTTPリクエスト / レスポンスの処理
- 入力値バリデーション（FormRequest等の責務）
- 複雑なクエリ構築（Repository層の責務。複雑化はDB設計の問題の可能性もある）
- 他のModelを介した間接的なデータ操作のオーケストレーション（Service層の責務）

### 判断基準

1. **ビジネスロジックの混入**
   - Model内にif文によるビジネス判定が存在しないか
   - 料金計算、ステータス遷移の可否判定、ポイント計算等のロジックがModel内にないか
   - スコープ内にビジネスルールが埋め込まれていないか（判定条件はエンティティ、クエリ条件はRepositoryの関心事）

2. **リレーション定義の適切性**
   - テーブル間の関係がリレーションとして正しく定義されているか
   - リレーションの命名がドメイン用語を反映しているか（`user`ではなく`purchaser`等）
   - 不要なリレーション（実際には使われていない定義）が残っていないか
   - リレーションを辿る際にN+1問題が発生していないか

3. **スコープの責務範囲**
   - スコープがクエリ条件の再利用に限定されているか
   - スコープ内でビジネスロジックに相当する複雑な条件判定を行っていないか
   - スコープの粒度が適切か（1つのスコープが複数の独立した条件を混ぜていないか）

4. **アクセサ / ミューテタの適切性**
   - アクセサがデータの表示変換に限定されているか
   - アクセサ内でビジネスロジック（計算、判定）を行っていないか
   - ミューテタがデータの保存変換に限定されているか
   - アクセサが他のModelやサービスに依存していないか

5. **Modelの肥大化**
   - 1つのModelに過度に多くのスコープ・リレーション・アクセサが定義されていないか
   - Model内のメソッド数が過度に多くないか
   - 本来Repository層やService層に属する処理がModelに集約されていないか

6. **データ整合性の保護**
   - fillable / guarded が適切に設定されているか（マスアサインメント脆弱性の防止）
   - 型キャストが適切に定義されているか
   - ソフトデリート使用時に関連データの整合性が考慮されているか

7. **永続化とドメインの境界**
   - ModelがORMの永続化モデルとしてのみ機能しているか
   - ドメインロジックが必要な場合、別のドメインオブジェクト（値オブジェクト、エンティティ）に分離されているか
   - テーブル構造の都合がアプリケーション全体のAPI設計に影響していないか

### 欠陥パターン

- **ファットモデル（Fat Model）**: スコープ、アクセサ、リレーション、ビジネスロジック、クエリ構築が全て1つのModelクラスに詰め込まれ、数百〜数千行に肥大化している。Model内のメソッドが何の責務に属するのか判別困難になっている
- **ビジネスロジックの混入**: 料金計算、ステータス遷移判定、権限チェック等がデータモデル内に実装されている。`$order->canCancel()`等はエンティティの振る舞いであり、データモデルに置くべきではない
- **スコープへのビジネスルール埋め込み**: `scopeActive()`等で「有効かどうか」の判定がスコープに埋め込まれている。これはエンティティの責務であり、スコープに埋め込むと変更箇所が分散する
- **God Model**: 1つのModelがアプリケーション全体で中心的な役割を担い、大量のリレーション・スコープ・メソッドを持つ。Userモデルが100以上のメソッドを持つような状態
- **Modelからの外部サービス呼び出し**: Modelのライフサイクルフック（creating, updated等）やメソッド内で、メール送信、API呼び出し、キュー投入等の外部サービスを直接呼び出している
- **アクセサでのロジック実装**: `getFullPriceAttribute()`のようなアクセサ内で、税率計算、割引適用、通貨換算等のビジネスロジックが実装されている
- **暗黙的なグローバルスコープ**: グローバルスコープにより、クエリの結果が暗黙的にフィルタリングされ、開発者が意図しないデータ欠落が発生する。特にソフトデリートのグローバルスコープが意図せず適用されるケース
- **Modelを介したクエリの直接構築**: Controller層やService層で`Model::where()->join()->groupBy()`のような複雑なクエリチェーンが直接構築され、クエリロジックがアプリケーション全体に散在している。これはRepository層に集約すべき
