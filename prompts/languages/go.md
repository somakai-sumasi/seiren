# 言語固有の観点: Go

以下はGo固有の欠陥パターンと設計観点である。コアプロンプトの共通観点に加えて、これらを分析に適用すること。

## エラーハンドリングの欠陥

- **エラーの握り潰し**: `_` でエラーを無視するのはバグの原因。必ず処理またはログ出力する
- **エラーラップのコンテキスト欠如**: `return err` ではなく `return fmt.Errorf("操作名: %w", err)` で文脈を付与する
- **カスタムエラー型の不使用**: センチネルエラー (`var ErrNotFound = errors.New(...)`) を定義し、`errors.Is` / `errors.As` で検査する。直接型キャストや文字列比較でのエラー判定は欠陥
- **panicによる制御フロー**: panicは回復不能なエラーにのみ使用。通常のエラーはerrorを返す

## カプセル化の欠陥

- **巨大なインターフェース**: 「Accept interfaces, return structs」が原則。インターフェースは利用側で定義し、1-3メソッドに保つ
- **パッケージレベルのグローバル状態**: パッケージ変数やinit関数で可変状態を管理するとテスト容易性と並行安全性が低下。コンストラクタ関数による依存注入を使用する
- **ゼロ値の未活用**: ゼロ値がそのまま使える型設計が推奨される。初期化が必要な `map` をフィールドに持つ場合はコンストラクタで初期化する

## 並行処理の欠陥

- **ゴルーチンリーク**: チャネルやコンテキストの適切な管理がないゴルーチンはリークする。バッファ付きチャネルと `select` + `ctx.Done()` を使う
- **errgroupの不使用**: `sync.WaitGroup` + エラーチャネルの手動管理は煩雑でバグを生みやすい。`golang.org/x/sync/errgroup` でエラー収集とキャンセル伝播を簡潔に記述する
- **context.Contextの不適切な使用**: 構造体に格納してはならない。関数の第一引数として渡す

## コンポジションの欠陥

- **Embedding未活用**: ラッパー関数を大量に書いて委譲するのは冗長。構造体Embeddingでメソッドを昇格させ、Goらしいコンポジションを実現する
- **is-a ではなく has-a**: Goに継承はない。インターフェースを満たすための委譲コードが増えている場合はEmbeddingへの置き換えを検討

## パフォーマンスの欠陥

- **スライスの事前割り当て欠如**: サイズが既知の場合、`make([]T, 0, n)` で事前割り当てすることで再割り当てを防ぐ
- **ループ内の文字列連結**: `+` による文字列連結は毎回新しい文字列を割り当てる。`strings.Builder` を使用する

## セキュリティの欠陥

- **シークレットのハードコード**: APIキーやパスワードの直接記述。環境変数を使用すべき
- **タイムアウトなしのHTTPクライアント**: `http.DefaultClient` のタイムアウト未設定。`context.WithTimeout` を使用すべき
- **SQLインジェクション**: 文字列結合によるSQL構築。プリペアドステートメントを使用すべき
- **gosecの指摘項目**: `gosec ./...` で検出される脆弱性パターン

## その他の欠陥パターン

- **naked return**: 長い関数でのnaked returnは可読性を低下させる
- **レシーバの不統一**: 同じ型で値レシーバとポインタレシーバが混在
- **パッケージ名の冗長さ**: `userService` のようなサフィックス付きパッケージ名
- **不要な外部依存**: 標準ライブラリで十分な処理に外部パッケージを導入
