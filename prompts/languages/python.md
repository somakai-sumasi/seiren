# 言語固有の観点: Python

以下はPython固有の欠陥パターンと設計観点である。コアプロンプトの共通観点に加えて、これらを分析に適用すること。

## 型安全性の欠陥

- **型アノテーションの欠如**: 関数シグネチャに型アノテーションがないコードは意図が不明確で保守性が低下する
- **Any型の乱用**: `Any` は型チェックを無効化する。外部入力は適切な型（dataclass等）で受け、型ガードで絞り込む

## カプセル化の欠陥

- **辞書の乱用（データクラスの欠如）**: ビジネスデータを辞書で持ち回すとキー名の不整合やバリデーション漏れが発生する。`@dataclass(frozen=True)` で型安全なDTOを定義する
- **Protocolの未活用**: Pythonのダックタイピングを型安全に活用するには `typing.Protocol` で依存を逆転させる

## 不変性の欠陥

- **ミュータブルなデータ構造**: ビジネスデータは `@dataclass(frozen=True)` や `NamedTuple` で不変にすべき。変更が必要な場合は新しいインスタンスを返す
- **ミュータブルなデフォルト引数**: `def f(items=[])` はバグの原因。`None` をデフォルトにして関数内で初期化する

## 関心の分離の欠陥

- **God Module**: 1つのモジュールにビジネスロジック、データアクセス、バリデーション、例外処理がすべて混在するパターン
- **パッケージ構造の不在**: すべてのコードが1ディレクトリにフラット配置。`domain/` / `repository/` / `service/` 等の関心ごとに分離する

## エラーハンドリングの欠陥

- **Exception Chaining の欠如**: `except` で捕捉した例外を再raiseする際に `raise X from e` を使わないと、元の例外情報が失われデバッグが困難になる。`raise X from None` は意図的な場合のみ許容
- **カスタム例外階層の欠如**: 汎用の `Exception` / `ValueError` を直接raiseすると呼び出し元で例外種別を区別できない。`AppError` → `NotFoundError` / `ValidationError` のようなドメイン固有の階層を定義する
- **bare except**: `except:` や `except Exception:` で全例外を捕捉。具体的な例外型を指定すべき

## Pythonイディオムの欠陥

- **LBYL スタイルの多用**: Python では EAFP（例外処理優先）が推奨される。事前条件チェックの連鎖は競合状態リスクとコードの冗長性を招く
- **Context Manager 不使用**: ファイル・DB接続・ロック等のリソース管理で `with` 文を使わず `try/finally` で代用するのはリソースリークの温床。`with` 文が使える状況での `try/finally` は欠陥

## セキュリティの欠陥

- **シークレットのハードコード**: APIキーやパスワードの直接記述。環境変数を使用すべき
- **eval/execの使用**: ユーザー入力を含む`eval()` / `exec()` はコードインジェクションの危険
- **pickleの安全でないデシリアライズ**: 信頼できないデータの `pickle.load()` は任意コード実行の危険
- **SQLインジェクション**: f-stringや `%` フォーマットによるSQL構築。パラメータバインディングを使用すべき
- **banditの指摘項目**: `bandit -r src/` で検出される脆弱性パターン

## その他の欠陥パターン

- **グローバル変数の乱用**: モジュールレベルの変更可能な状態
- **リスト内包表記の過剰なネスト**: 3重以上のネストは可読性を著しく低下させる
- **import ***: ワイルドカードインポートは名前空間を汚染する
- **未使用のインポート**: コードの可読性低下とモジュール読み込みの無駄
